## Remaining risks and limitations

- No authentication or authorisation; the API must not be exposed beyond a trusted machine.
- Open business rules (see business-rules.md) may change some figures, notably LWE "Overall".
- The workbook is parsed in about 10 s on first use and again after each change; each server process holds its own cache.
- Only the current month in the workbook is analysed; earlier monthly columns (Oct-25 to Sep-26) aren't yet surfaced.
- Raw CSV ingestion, the LWE ID mapping and 2100 MHz selection aren't implemented; the mapping reference file isn't in the repository.
- The frontend tests don't cover the charts' visual output; charts were checked manually.
- `match_master.py` still targets 4G MP by design (constants at the top of the script).

## Addendum (22 Oct 2026): workbook upload flow

**Requirement.** The dashboard must be driven by the consolidated workbook *uploaded through the application*. `Data/reference/` holds a copy for inspection only and will be removed.

**Changes.**

| Area | Change |
|---|---|
| Data source | The active dataset is the latest accepted upload (`Data/processed/workbooks/`, pointer `active.json`). `Data/reference/` is no longer read. `MASTER_WORKBOOK_PATH` remains only as a fallback when nothing has been uploaded. |
| Upload API | `GET/POST /api/dashboard/workbook/`. Checks: `.xlsx` only (`.xlsm` refused), size limit, genuine OOXML package, no VBA project, expanded-size limit, full sheet validation, at least one reported date. Staged first; activated by an atomic pointer swap only after every check passes. Rejections return the problems and state that the previous workbook is still in use. |
| Formula handling | Pandas/openpyxl read cached formula results and never recalculate. All KPIs are recalculated from raw outage minutes; formula cells in `Up-Time Report` without cached results are detected and reported (separately when they fall in the daily outage block). |
| Sheets | All 13 sheets are listed with their role on the Master workbook and Data source pages. |
| New figures | Monthly uptime history (from `<Mon-YY> Outage Min.` columns), uptime per CI and IE, daily site bucket distribution. |
| Frontend | Master workbook page (drag-and-drop, upload progress, validation result, workbook in use). Dashboard shows an upload prompt (no sample data) when nothing is loaded; every query key includes the workbook version so a new upload refreshes all panels. The header upload button opens this page; the old raw-file modal was removed (raw CSVs remain on the Raw CSV files page). |
| Tests | Test runner isolates the workbook store; new upload, formula, monthly and team tests; monthly reconciliation. |

**New workbook revision.** The reference workbook was replaced on 22 Oct (11:00). Its `Up-Time Report` site data is identical to the 19 Oct revision (all 6,726 rows, attributes and daily values compared); only summary sheets grew. All reconciliation tests pass against it.

**End-to-end verification (live servers).**

- The workbook was uploaded through the browser UI at 11:30 (`POST /api/dashboard/workbook/` → 201 in ~13 s); the stored copy is byte-identical to the reference file (MD5).
- Rejections against the live server, each leaving the active workbook unchanged and no staging files behind: a CSV renamed `.xlsx` (422), an `.xlsx` without `Up-Time Report` (422), an `.xlsm` (400).
- Filters on the live API: the 11 circles sum to All circles (6,726); MP = 1,483 4G + 22 LWE; MP and RJ return disjoint subsets; different reporting dates return different daily and MTD values.
- Screenshots of the dashboard (all panels including monthly and team performance) and the Master workbook page were checked against the API values.

**Limitations.**

- Monthly history is recomputed with today's On-Air / O&M flags and can differ from the frozen figures in `Summ` for some months (documented in business-rules.md).
- `Repeated Sites`, `Signoff status` and `One Pager Summary` are static or manual sheets without derivable definitions and are not shown.
- Upload validation runs in the request (about 10–20 s). That is adequate for a single local user; multi-user use would need a background job and authentication.
